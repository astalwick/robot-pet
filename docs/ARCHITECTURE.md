# Architecture

## Overview

The robot runs on a Raspberry Pi 5 under Ubuntu 26.04 with ROS 2 Lyrical. Every
process is a systemd unit. The ones that touch motion, sensing and power are
ROS nodes; the rest (dashboard, camera, voice, vision) are plain Python
services that talk over a local telemetry hub. There is no colcon workspace:
nodes are plain Python files in `src/ros_nodes/` run by `scripts/ros-node.sh`,
which sources `/opt/ros/lyrical/setup.bash`, loads
`~/.config/robot-pet/ros.env` (`ROS_DOMAIN_ID`, CycloneDDS pinned to loopback, localhost-only
discovery) and execs the repo venv's python.

The migration plan and its phase-by-phase record live in
[plans/done/2026-07-10 - ros2-migration.md](plans/done/2026-07-10%20-%20ros2-migration.md).

## Guiding Principle

**Drivers are framework-agnostic. Nodes and services are thin.**

Code that talks to hardware (`src/drivers/`) is pure Python with no ROS or
systemd imports. The same goes for the geometry (`robot_model.py`), kinematics
(`control/`) and the service loops (`robot_motion.py`, `robot_sensors.py`,
`robot_pi_battery.py`, `gamepad_teleop.py`). A ROS node is a small file that
builds one of those loops, hands it a publish callback, and spins. That keeps
every loop testable on a Mac without rclpy.

## Directory Structure

```
src/
├── control/              # Teleop policy, differential-drive kinematics, odometry
├── drivers/              # Hardware drivers: RoboClaw, gamepad, camera, VL53 ToF, IMU, UPS HAT
├── config/               # Persistent runtime config helpers (drive tuning, sensors)
├── lib/log.py            # Logging setup (journald-friendly)
├── telemetry/            # JSON messages + Unix-socket client for the local hub
├── ros_nodes/            # One file per ROS node (see table below) + ros_messages.py
├── robot_model.py        # Physical geometry: wheels, footprint, sensor mounts
├── robot_motion.py       # Motion loop: RoboClaw owner, safety gating, voice intents
├── robot_sensors.py      # Sensor loop: ToF + IMU polling
├── robot_pi_battery.py   # Pi battery loop: UPS HAT E
├── gamepad_teleop.py     # Teleop loop: gamepad -> twist
├── robot_battery.py      # Motor-rail MOSFET and LiPo protection
├── robot_telemetry.py    # Local telemetry hub
├── robot_camera.py       # Pi camera owner; serves MJPEG/snapshot
├── robot_vision.py       # Face detection on camera snapshots
├── robot_voice.py        # Voice assistant
├── robot_web_dashboard.py # Browser dashboard
├── robot_dashboard.py    # SSH Textual dashboard
└── web_dashboard_static/ # HTML/CSS/JS for the browser dashboard (no build step)

urdf/robot.urdf           # Generated by scripts/generate-urdf.py from robot_model.py
config/twist_mux.yaml     # /cmd_vel arbitration
systemd/*.service         # One unit per process
scripts/ros-node.sh       # ROS env + venv python wrapper used by every node unit
```

| `robot-pi-battery` | ROS node | `pi_battery_node.py`: UPS HAT E; publishes `/battery/pi` |
| `robot-motion` | ROS node | `motion_node.py`: RoboClaw owner; subscribes `/cmd_vel`; publishes `/odom`, TF `odom -> base_link`, `/battery/motor`; hosts voice motion intents |
| `robot-twist-mux` | ROS (apt) | `twist_mux`: `/cmd_vel_teleop` (priority 100) and `/cmd_vel_nav` (priority 10, Nav2), muted by `/nav_lock` while an intent runs -> `/cmd_vel` |
| `robot-lidar` | ROS (apt) | `rplidar_driver` via `config/rplidar.launch.py`: RPLidar A1 on `/dev/rplidar` -> `/scan` in the `laser` frame; udev starts/stops it with the device; starts configured but inactive, lifecycle `activate`/`deactivate` turns the lidar on/off |

| `robot-lidar-status` | ROS node | `lidar_status_node.py`: watches `/scan`, `/diagnostics` and the lidar/nav units; publishes lidar health to the hub for the dashboard; activates the lidar when the hub's `motor_rail` comes on and deactivates it 3 s after it drops; a driver that starts with the board off is activated and deactivated once, as the A1's motor spins from the moment its port opens |
| `robot-nav-bridge` | ROS node | `nav_node.py` + `robot_nav.py`: owns `nav.json`, `places.json`, `barriers.json`, `maps/` and `keepout/`; serves `/run/robot-pet/nav.sock` (save map, switch mode, localize, create or delete a place, draw or delete a barrier, navigate, cancel) for the dashboard and voice; judges each lidar scan against the map and drops a pose the scans contradict, unless the scan matches the last good one carried by the wheels (the self-check); notices the robot picked up or pushed (cliff sensors, IMU) and checks the pose afresh once it is put down; searches every saved map for the robot's place (on a background thread) when lost, and every few seconds while held to catch a slip; publishes the `nav` hub message and `/run/robot-pet/map.png` |
| `gamepad-teleop` | ROS node | `gamepad_teleop_node.py`: Xbox controller -> `/cmd_vel_teleop` |
| `robot-camera` | service | Owns the Pi camera; serves MJPEG stream and JPEG snapshots over HTTP |
| `robot-vision` | service | Polls camera snapshots, publishes face-detection telemetry |
| `robot-voice` | service | Voice assistant (ReSpeaker, LLM tools incl. motion intents) |
| `robot-web-dashboard` | service | Browser dashboard: camera, telemetry, logs, redeploy, drive tuning |
| `robot-foxglove` | ROS (apt) | `foxglove_bridge` on ws://robot:8765 |
| `robot-dashboard` | manual | Foreground SSH TUI |

Start order is the `ROBOT_SERVICES` array in `setup.sh`; `restart.sh` and
`scripts/redeploy-robot.sh` mirror it, and a test fails if the lists drift.

### Dual publish

Nodes keep publishing their JSON hub messages for the dashboards and also
publish the ROS message. The hub is still what the dashboards, robot-battery
and robot-voice read; ROS is what Foxglove, slam_toolbox and Nav2 read.
`ros_nodes/ros_messages.py` holds the pure conversions from hub dicts to ROS
message fields so they stay testable without rclpy.

The apt lidar driver only speaks ROS, so `robot-lidar-status` goes the other
way: it summarizes `/scan` and `/diagnostics` into a `lidar` hub message, and
the dashboard's Lidar panel reads that like any other panel. It is also the
only thing that turns the lidar on and off by itself: the lidar follows the
motor rail, so it spins only while the robot can move. The dashboard button is
a manual override that holds until the rail next switches.

### Motion and safety

`robot-motion` owns `MotorDriver` / RoboClaw. It takes wheel targets only from
`/cmd_vel`, which `twist_mux` builds from `/cmd_vel_teleop` and Nav2's
`/cmd_vel_nav`. A stale `/cmd_vel` (`DRIVE_COMMAND_STALE_SECONDS`) stops the
motors; the teleop node publishes one zero twist when the sticks are released
(and on controller loss or stop) and then goes quiet, so the deadman is the
backstop and a paired but idle controller does not mute Nav2 in `twist_mux`. Safety gating
(`control/safety_gate.py`) reads thresholds from `sensors.json`: the ToFs cover
cliffs and low obstacles ahead, and `/scan` covers the rest. `motion_node.py`
reduces each scan to the nearest return in the body's width past the front and
rear edges, and a return closer than `lidar_stop_below_mm` blocks driving that
way (`lidar_forward_obstacle`, `lidar_rear_obstacle`). Turning in place is
never blocked, and a scan older than 1 s switches the lidar rule off, so with
the rail off (lidar idle) only the ToFs gate. Voice motion intents arrive on
`/run/robot-pet/motion-intent.sock` and are interrupted by any non-zero
`/cmd_vel`, which today means gamepad activity.

`robot-battery` owns the high-side MOSFET on the LiPo motor rail. It stays
running when the rail is off and applies the power policy from
[body-phase-2.md](phases/body-phase-2.md#robot-battery--motor-rail-power). It
does not open RoboClaw serial; that stays `robot-motion`.

### Frames

`robot_model.py` is the source of truth for geometry, in REP-103 `base_link`
(origin at the drive-axle midpoint on the ground, +x forward, +y left, +z up).
`scripts/generate-urdf.py` renders it to `urdf/robot.urdf`; a test fails if the
checked-in file is stale. `robot-state-publisher` broadcasts the fixed joints
on `/tf_static`, `robot-motion` broadcasts `odom -> base_link`. Each Range
message uses its mount name as `frame_id`, so Foxglove draws readings at the
sensor. Measured dimensions are in [robot dimensions.md](robot%20dimensions.md)
and [forward tof sensor geometry.md](forward%20tof%20sensor%20geometry.md).

### Camera, vision, dashboards

`robot-camera` is the only owner of the Pi camera. It captures JPEG frames
continuously and serves them over HTTP (`GET /snapshot.jpg`,
`GET /stream.mjpg`); the dashboard and `robot-vision` subscribe over HTTP
rather than opening the camera. Video never goes through the telemetry hub.

`robot-vision` runs OpenCV face detection on snapshots and publishes
normalized face boxes to the hub. It honors `enabled` in
`~/.config/robot-pet/vision.json` and idles when disabled.

`robot-web-dashboard` serves the operator UI, logs, action endpoints and an
SSE telemetry stream on port 8080. It writes drive tuning to
`~/.config/robot-pet/drive_tuning.json` and restarts `gamepad-teleop` and
`robot-motion` to apply it. `robot-dashboard` is the same thing as an SSH TUI.

## Driver Guidelines

Drivers in `src/drivers/` must:

1. **Be pure Python classes**: no ROS or systemd imports.
2. **Have no logging framework dependency**: accept an optional logger, or don't log.
3. **Be testable in isolation**: instantiate and test without running any service.
4. **Expose clean interfaces**: `set_speed(left, right)`, not `handle_ros_message(msg)`.

## Node Guidelines

A node in `src/ros_nodes/` is one `rclpy.node.Node` subclass plus a `main()`:

1. Parse args, `rclpy.init()`, build the node and the service loop with
   `publish=node.publish`.
2. Run the loop with `ros_nodes/service_thread.py` (`start_service_thread`); `rclpy.spin(node)` on the main thread. If the loop ever dies, the helper shuts rclpy down so the process exits and systemd restarts it.
3. Catch `(KeyboardInterrupt, ExternalShutdownException)`, stop the loop,
   join, clean up hardware, `rclpy.try_shutdown()`.

Conversions from hub dicts to ROS fields go in `ros_messages.py`, not the node.

## Logging

All services log to stdout/stderr; systemd captures to journald.

- One unit: `journalctl -u robot-motion -f`
- Several: `journalctl -u robot-motion -u robot-sensors -u gamepad-teleop -f`
- Format: `LEVEL service-name: message`; timestamps come from journald.

## Lidar, maps and navigation

The lidar work is tracked in
[plans/2026-10-12 - lidar.md](plans/2026-10-12%20-%20lidar.md) and the safety
and navigation work in
[plans/2026-10-25 - lidar-safety-and-nav2.md](plans/2026-10-25%20-%20lidar-safety-and-nav2.md).

`robot-lidar.service` publishes `/scan` in the `laser` frame; the URDF has a
`laser` frame from the measured `LIDAR_MOUNT` (82 mm behind the axle, scan plane
203 mm up). The TF tree is `map -> odom -> base_link -> laser`. The lidar also
feeds the motion node's safety gate (`control/safety_gate.py`): the nearest
scan point inside the footprint's lane blocks forward or reverse like the ToFs
do, so the robot stops for things the ToFs cannot see.

`robot-nav.service` has two modes, picked by `~/.config/robot-pet/nav.json`.
A fresh robot (no `nav.json`, or its map file gone) **maps**: slam_toolbox
builds `/map` as you drive with the gamepad. "Save map" writes
`~/.config/robot-pet/maps/<name>.yaml` + `.pgm` with `map_saver_cli` and
switches to **localize** mode on that map: `map_server` serves it and AMCL
tracks the robot against it. Places (`~/.config/robot-pet/places.json`) are
poses on a named map, saved only while localized, so they survive reboots.

`robot-nav-bridge.service` (`ros_nodes/nav_node.py`, logic in `robot_nav.py`)
is the only writer of those files and the only thing that restarts `robot-nav`
to switch modes. Whenever AMCL comes up it either sends the pose it remembered
in `/run/robot-pet/nav-pose.json` (same map, not rebooted) or **searches**:
`robot_nav.global_search` scores the latest scan at every pose on every saved
map, and a clear winner named by two searches in a row is handed to AMCL as
its initial pose, loading that map first if it is another floor. That is how
a robot carried to another floor works out which map it is on. `/run` is
tmpfs, so a reboot always searches. The search runs on its own thread, back
to back while the robot does not know where it is and every few seconds while
it does, to catch a slip. The robot never moves itself to search.

AMCL's own confidence (its pose covariance) is not used: AMCL only grades its
particles against each other, so a robot carried to another room keeps a
confident wrong pose. Every tick the bridge judges the latest scan against the
map from the lidar's pose (`robot_nav.beam_check`: beams that agree with a
wall, and beams that went through one), and one state says how far the pose
is trusted: tracking, checking, searching, or stale while the lidar is off. A
run of failed scans drops the pose (the remembered pose goes and a trip in
progress is cancelled), unless the scan matches the last one that passed,
carried by the wheels (`robot_nav.scan_check`, the self-check: the room
changed there). The bridge also notices the robot picked up (the cliff
sensors) or pushed (the IMU) and checks the pose afresh once it is put down.
A `navigate_to` while the robot does not know where it is waits for the
search, then goes. The bars and switches are in `localization.json`; the
design and the floor measurements behind them are in
`docs/plans/2026-10-26 - localization-plan.md`.

Both modes also run the Nav2 navigation servers (planner, controller,
behaviors, bt_navigator) from `config/nav2.yaml`, with the robot's footprint
from `robot_model.py` (the local costmap, for the controller's collision
check) and its half width as the global costmap's radius (the planner plans
for a point; see the comment in the yaml), and the lidar as the costmap
obstacle source. Their
`/cmd_vel_nav` is the lowest `twist_mux` input, below the gamepad. The servers
are launched but not activated: their costmaps need the `map` frame, which
only exists once the lidar is scanning, and the lidar follows the motor rail.
The nav bridge activates them once the robot is scanning and has a map pose,
and pauses them again five seconds after the scans stop (without scans the
`map -> odom` transform stops advancing, and once it falls out of TF's 10 s
cache every costmap lookup fails and logs). So Nav2 comes up per trip.
The bridge is also the only Nav2 action client: `navigate_to` (a place name,
or map x/y from a click on the dashboard map) returns at once, asks for the
motor rail, and opens a trip that is `held` (with `waiting_for` the lidar,
the position or Nav2) until the lidar, a sure pose and Nav2 are up, then sends
one `NavigateToPose` goal (`navigating`, with metres remaining). A trip whose
pose drops, or whose robot is picked up, stops and is held again, and goes on
by itself once the robot is sure of its place (`resume_trips`); a trip held
more than `hold_s` in all, or with the robot off the map, fails. A place on
another saved map is held while the robot is unsure of its place, in case
the search finds it on that map. The trip's state (`held`, `navigating`,
`arrived`, `cancelled`, `failed`, plus a reason) rides the hub as `nav.goal`.
Asking for the place already being driven to keeps the trip; another place
replaces it. `nav_cancel` or a mode switch cancels a trip, and gamepad input
cancels a driving one (a held trip waits for exactly that push).
`localization.json` holds the timings.

Voice intents win over Nav2 through `/nav_lock`: the motion node publishes it
true while an intent runs and for two seconds after a stop, `twist_mux` mutes
`/cmd_vel_nav` while it is true, and the bridge cancels the goal (reason
`stopped`) and refuses new ones (`wheels_busy`) while the lock is held. So
"stop" halts the wheels and the trip in the same moment, and "go to the
kitchen" mid-route simply replaces the goal. The voice tools are
`navigate_to` (waits up to `trip_wait_s` for a trip held on the position to
leave, so a quick find needs no explaining), `check_navigation` (polls the
bridge up to a minute), `cancel_navigation`, `create_place` and `where_am_i`
(map, localized, nearest place); their results carry a note for a held,
lost or off-the-map trip. The `stop` tool and a bare spoken "stop" or
"cancel" (which starts no turn) also send `nav_cancel`.

**Barriers** are lines drawn on the dashboard map that Nav2 treats as walls
(the steps down to the dining room look like open floor to the lidar). They
live per map in `~/.config/robot-pet/barriers.json`. The bridge paints the
current map's barriers as a Nav2 keepout mask, a small occupancy grid in the
map frame with each line a 0.6 m wide black band (keepout cells are not
inflated, and the tail sweeps 0.31 m when the robot turns), into
`~/.config/robot-pet/keepout/<map>.yaml` + `.pgm`. `nav.launch.py` serves it
with a second `map_server` (`filter_mask_server`) and
`costmap_filter_info_server`, and both costmaps carry a `keepout_filter`.
After a barrier is drawn or deleted the bridge re-renders the mask and calls
`/filter_mask_server/load_map`, so the next plan sees it without a restart.
The gamepad never meets Nav2, so the bridge also publishes `/barrier_clearance`
(the body's room to the nearest barrier ahead and behind, 10 Hz, only while
localized) and `robot-motion`'s safety gate stops 0.2 m short of a line the
way it stops short of a lidar return. Not localized: no message, no rule.
A robot already inside a band cannot plan its way out; drive it out by gamepad.
See [plans/2026-10-25 - virtual-barriers.md](plans/2026-10-25%20-%20virtual-barriers.md).
