# Lidar + SLAM Plan

Goal: an RPLidar A1 publishing `sensor_msgs/LaserScan` on `/scan`, a `laser`
frame in the URDF, and slam_toolbox building a live map in Foxglove while the
robot is driven around a room with the gamepad. This is the "drop in a lidar
node and slam_toolbox next" step the
[ros2-migration plan](done/2026-07-10%20-%20ros2-migration.md) left room for.
Nav2, map persistence and LLM navigation goals are **not** in this plan.

Everything installs through `setup.sh` and redeploys through
`scripts/redeploy-robot.sh`; nothing is set up by hand on the robot.

## Hardware facts (2026-10-12)

- RPLidar A1 over USB. Appears as a Silicon Labs CP2102 UART bridge,
  `idVendor=10c4 idProduct=ea60`, serial number `0001` (generic), today at
  `/dev/ttyUSB0`. It is the only CP210x on the robot, so matching by
  vendor/product is enough.
- `pi` is already in `dialout`, so the port is readable without a new group.
- A1 talks at 115200 baud, 12 m nominal range, ~5.5 Hz scan rate at 8000
  samples/s. The 0° mark is on the opposite side from the motor and cable.

## Decision record

| Decision | Choice |
|---|---|
| Driver | apt `ros-lyrical-rplidar-driver` (1.4.2, frozenreboot's lifecycle rewrite of rplidar_ros). `rplidar_ros` is listed for Lyrical but was never built, so apt cannot find it. Run as `ros2 launch rplidar_driver rplidar_with_args.launch.py ...` from a systemd unit; the launch file does the lifecycle configure/activate. No source build. |
| Device path | udev rule in `setup.sh` gives the lidar a stable `/dev/rplidar` symlink and tags it for systemd. The unit binds to the device, so it starts when the lidar is plugged in and stops when it is unplugged. |
| Frame | `frame_id=laser`, mount in `robot_model.py`, URDF `laser` block uncommented. |
| SLAM | slam_toolbox online async via its stock `online_async_launch.py` with our params file in `config/`. This is the first `ros2 launch` in a unit; slam_toolbox is a lifecycle node and its launch file handles configure/activate. |
| Map persistence | Deferred. Mapping mode only; the map is rebuilt every boot. |

## Phase 0 - Mount and measure (Arlen)

Done 2026-10-25: measurements are in `docs/robot dimensions.md` and
`LIDAR_MOUNT`; the wall test in Foxglove confirmed the orientation.

1. Mount the lidar rigidly on the mast with the scan plane clear of the face
   and everything on the deck. The shopping list suggested 280-320 mm above
   the floor; what matters is that nothing on the robot sits in the plane.
2. Measure and write into `docs/robot dimensions.md`:
   - lidar rotation-centre forward (+) or behind (-) the drive axle, mm
   - left (+) or right (-) of the centreline, mm (aim for 0)
   - height of the scan plane above the floor, mm (the A1 scan plane is
     roughly the top of the black rotating head, not the base)
   - which way the 0° mark points relative to the robot's front. Straight
     ahead is yaw 0; pointing backwards is yaw π.

The driver can be brought up before this is done; only Phase 2 needs it.

## Phase 1 - Driver node

- `setup.sh`: add `ros-lyrical-rplidar-driver` to the ROS apt install line.
  Add a udev rule next to the ReSpeaker one:
  `SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", SYMLINK+="rplidar", TAG+="systemd"`.
- `systemd/robot-lidar.service`: `ConditionPathExists=/dev/rplidar`, ExecStart
  through `bash -c 'source ... && exec ros2 launch rplidar_driver
  rplidar_with_args.launch.py serial_port:=/dev/rplidar serial_baudrate:=115200
  frame_id:=laser angle_compensate:=true publish_tf:=false'`. `publish_tf` is off
  because the URDF owns `base_link -> laser`. Topic defaults to `/scan`.
- Service lists: `setup.sh` (both arrays), `redeploy-robot.sh` (three lists,
  plus a case so `systemd/robot-lidar.service` restarts it), `restart.sh`
  (lists, `lidar)` alias, known-services string), `tests/test_redeploy_robot.py`.
- Verify on the robot: `ros2 topic hz /scan` near 5-7 Hz; Foxglove 3D panel
  shows the scan ring. Unplug the lidar: the unit stops. Plug it back in: it
  starts again without a redeploy.

Why the udev start/stop: the unit's `ConditionPathExists=/dev/rplidar` makes a
start without the lidar a clean no-op, so the device appearing has to be what
starts it. The udev rule tags the port for systemd and names the unit in
`SYSTEMD_WANTS`; a matching remove rule stops it.

## Phase 2 - Laser frame

- `src/robot_model.py`: `LIDAR_MOUNT = SensorMount("laser", x=..., y=..., z=..., yaw=...)`
  from the Phase 0 measurements.
- `scripts/generate-urdf.py`: replace the commented block with a real
  `laser` link and fixed joint from `LIDAR_MOUNT`; regenerate `urdf/robot.urdf`.
  Keep the "no `: ` or ` #` in the URDF" rule (rcl parses it as YAML).
- `tests/test_generate_urdf.py`: the laser joint origin matches `LIDAR_MOUNT`.
- Verify: in Foxglove with `base_link` as the fixed frame, the scan hits on a
  wall straight ahead line up with what `/range/forward_center` reports, and
  the ring is the right way round (walls to the robot's left appear at +y).
  A mirrored ring means the yaw is off by π or `inverted` needs to be true.

## Phase 3 - slam_toolbox

- `config/slam_toolbox.yaml`: copy of the stock `mapper_params_online_async.yaml`
  with `base_frame: base_link`, `scan_topic: /scan`, `max_laser_range: 12.0`,
  `mode: mapping`. Leave the rest at defaults until the map says otherwise.
- `systemd/robot-slam.service`: `After=robot-lidar.service robot-motion.service
  robot-state-publisher.service`, ExecStart
  `ros2 launch slam_toolbox online_async_launch.py slam_params_file:=/home/pi/robot-pet/config/slam_toolbox.yaml`.
  Add to the service lists as in Phase 1, with a case for `config/slam_toolbox.yaml`.
- Verify: `ros2 run tf2_tools view_frames` shows `map -> odom -> base_link -> laser`.
  Foxglove map panel on `/map`. Drive a loop around one room with the gamepad
  and come back to the start; the map should close without a visible seam.
  Record `free -m` and `top` CPU for the slam process with everything running
  (migration baseline: ~2.8 GB available before slam).
  Measured 2026-10-12 with every unit running and the robot stationary:
  2.1 GB available, 0 swap, load average 1.4, ~12 % total CPU; slam_toolbox
  was not in the top processes (it only works while scans change).
- `docs/ARCHITECTURE.md`: services table, frames, replace the lidar-readiness
  checklist with what is now true.

## Exit criterion

Boot the robot, drive it around a room with the gamepad, and watch a coherent
map build in Foxglove. All units come up from systemd with no manual steps,
and `./setup.sh` on a fresh card installs everything this plan added.

## Risks

| Risk | Mitigation |
|---|---|
| Mast flex gives subtly wrong maps | Rigid U-channel mount; check the scan ring does not wobble in Foxglove while driving. |
| Wheel diameter is nominal (0.97 m measured per 1.00 m commanded) | Odometry is 3 % long. slam_toolbox tolerates this for one room. Calibrate `WHEEL_DIAMETER_METERS` before Nav2, not before this plan. |
| Lidar node idles instead of exiting on a bad port | Device-bound unit (Phase 1). If a stuck node ever shows up, `restart.sh lidar`. |
| slam_toolbox CPU/memory on the Pi 5 | Measured in Phase 3. If it hurts, raise `minimum_time_interval` and `throttle_scans` before anything else. |
| First `ros2 launch` in a unit | slam_toolbox's launch does the lifecycle transitions for us. If it misbehaves under systemd, fall back to `ros2 run slam_toolbox async_slam_toolbox_node` plus `ros2 lifecycle set` calls in `ExecStartPost`. |
| Twist deadman vs slam | Unaffected: slam only listens to `/scan` and TF. |
