# UX audit: how the systems interact badly

Read-only review of the `ros2-nav2` branch on 2026-10-26. Nothing here is
fixed yet. Items marked **seen** happened in the robot's journals between
2026-10-23 and 2026-10-26 (times are the journal's monotonic seconds). The rest
are confirmed from the code. Ranked worst first inside each group.

The architecture section at the end says which of these collapse into a few
core changes.

## Talking and tool calls

1. **Nothing is spoken until every tool finishes.** The model's text streams
   first, then tools run one after another inside the same turn, then a second
   model call produces the reply (`src/voice/assistant.py` stream_openai_words,
   ~560-640). A tool call with no text means silence for the whole tool. The
   prompt only asks for a spoken heads-up before `web_search` and `end_session`
   (`config/operational_system_prompt.md`). Seen: with the rail off, `express
   wiggle` sits ten seconds waiting for the motor board (333.9→343.0,
   971.4→981.3, 688.7→699.0) then fails, then the robot speaks.
   Fix hint: speak before any motion/nav tool, or play a canned acknowledgement
   when the first tool call arrives with no text.

2. **One spoken word before a tool makes the robot "speaking" for the whole
   tool.** `_speak` only flips status back to listening in its `finally`
   (`src/voice/session.py:244-246`), and the barge-in judge is told the robot is
   speaking whenever the turn has an open playback slot, even in silence
   (`assistant.py:446-448`). Normal speech is rejected as too quiet. Seen:
   "commit rejected during playback: reason=low_rms" at 23910.7 and 23922.8
   while check_navigation ran and the robot was silent. Side effects: dashboard
   says "speaking"; the sound-direction tracker ignores the mic
   (`src/robot_voice.py:806`).
   Fix hint: judge barge-in on whether audio is actually playing.

3. **check_navigation freezes the conversation for up to 60 s.** Blocking poll
   in a thread (`src/voice/tools.py:684-697`, CHECK_NAVIGATION_MAX_WAIT_SECONDS).
   Seen: 22829→22862 (33 s), 23847→23907 (60 s). With item 2 this is "you can't
   talk while it navigates".
   Fix hint: return at once; let the nav bridge report arrival as an event.

4. **The text-to-speech socket dies during long tools.** ElevenLabs closes an
   idle socket after ~20 s; the URL never asks for a longer idle timeout
   (`src/voice/elevenlabs_io.py:434`). `play_audio` breaks on close; the next
   send fails and reopens. Seen: "elevenlabs tts send failed; retrying" at
   22863.9, 23342.5, 23375.0, 23713.6, 23748.7, one after every long
   check_navigation. Text buffered before the tool is lost; the reply pays a
   cold connection.
   Fix hint: pass `inactivity_timeout`, or close before a tool and reopen after.

5. **A turn dies after two long tool calls.** Hard 120 s turn timeout
   (ASSISTANT_TURN_TIMEOUT_SECS, `assistant.py:1225`) counts tool time. Seen:
   "assistant turn failed: TimeoutError" at 23965.6 after two check_navigation
   calls; status error, nothing spoken, trip kept going.
   Fix hint: time model calls only.

6. **Saying "stop" does not stop the robot.** A bare stop/wait/no/cancel (≤3
   words) is `interrupt_only` and never becomes a turn
   (`src/voice/turn_policy.py` commit_decision; `assistant.py:1455-1462`).
   During speech it only cuts audio (`assistant.py:1440-1444`). Only the model's
   `stop` tool halts motion or cancels a trip, and the model never hears the
   word.
   Fix hint: on an explicit interrupt word, call motion stop and nav_cancel
   directly.

7. **Cancelling a turn or ending the session leaves the robot moving.**
   Barge-in, a new turn, idle timeout and the dashboard End button cancel the
   Python task, but the motion intent completes in robot-motion and a trip keeps
   driving; nothing sends stop (`assistant.py:288-293`, `1041-1050`;
   `src/voice/agent_runner.py:373-387`). Seen: end-session at 27216 while
   check_navigation ran; trip failed on its own at 27257.
   Fix hint: cancelling a turn/goal that issued a body tool sends stop +
   nav_cancel.

8. **After move/turn/face_me the robot takes a photo before replying.**
   attach_motion_observation fetches telemetry plus a camera snapshot and sends
   an image before the follow-up speech (`assistant.py` ~600-620). Seconds of
   silence after every move.
   Fix hint: only attach the image when the model asked to look.

9. **Goal progress narration is silently dropped** while a line is being
   spoken or another narration is in flight (`agent_runner.py:318-328`). Goal
   time budget excludes tool time; stop flag only checked between steps.

10. **Any ≥4-word utterance cancels a running goal** (`assistant.py:1417`),
    e.g. the TV or another person, without stopping motion in flight (item 7).

11. **scan blocks for up to five turns plus photos in one tool call**
    (`src/voice/tools.py` _scan). Up to a minute of silence inside a goal step.

12. **A slow transcript commit is dropped.** 2 s after speech ends the commit
    is abandoned (SCRIBE_COMMIT_TIMEOUT_SECS, `elevenlabs_io.py`) and the
    user's sentence vanishes with no feedback.

## Driving, navigation and power

13. **Bug: relocalizing before a trip cancels the trip.** `navigate_to` marks
    the goal "navigating" at once (`src/ros_nodes/nav_node.py:720`). If not
    localized, the tick starts a relocalize (`753-758`). The spin is a motion
    intent, which raises the wheels lock (`src/robot_motion.py:775-781`,
    `src/ros_nodes/motion_node.py:93`), and `on_nav_lock` cancels any goal with
    reason "stopped" with no guard (`nav_node.py:207-210`). "Go to the kitchen"
    while lost spins twice and never leaves. The same handler kills a trip when
    a wiggle or dashboard Localize fires mid-trip. Seen: "relocalize: trying
    groundfloor" 27322.13, "navigation cancelled: stopped" 27322.19.
    Introduced in commit 088d237 (relocalize-before-goal); no Mac test covers
    nav_node.
    Fix hint: skip the cancel while `self.activity == "localizing"`, or only
    cancel when Nav2 actually holds the goal.

14. **Safety bug: a dead distance sensor turns cliff/obstacle guarding off
    silently.** Sensor status error/disabled/driver_unavailable publishes
    `readings=[]` (`src/robot_sensors.py:203-212`); robot-motion treats a fresh
    source as live (`robot_motion.py:283`); no readings means no trip
    (`src/control/safety_gate.py:122-143`). Telemetry says live, the robot
    drives off a step.
    Fix hint: treat `sensors.status != "ok"` or a configured sensor
    missing/`ok: False` as `sensors_stale`.

15. **The test suite flips the real motor rail on every setup and redeploy.**
    `setup.sh:381` and `scripts/redeploy-robot.sh:299` run unittest with
    services live; gamepad tests build the runner with the default publisher
    (`tests/test_gamepad_teleop.py:104-110` etc.; `src/gamepad_teleop.py:49,60,
    136,175`) and publish connected=True/False into the live hub. Battery turns
    the rail on then off; lidar follows; Nav2 pauses if >5 s.
    Fix hint: fast_config() passes a no-op telemetry publisher.

16. **Restarting robot-battery or the hub drops the rail mid-drive.** Battery
    turns the rail off on exit (`src/robot_battery.py:85`); a hub restart
    empties `latest` so everything reads stale → idle_no_gamepad. Redeploy
    restarts these for any telemetry/lib change (`redeploy-robot.sh:90-99,151`).
    Fix hint: redeploy refuses while the rail is on or a trip is running.

17. **A dead controller with centred sticks keeps rail and lidar on forever.**
    Dead reader only noticed when the stick is pushed
    (`gamepad_teleop.py:146-149`); keeps publishing connected=True.

18. **BUG, TO FIX FIRST. Wall switch off is invisible, and the lidar spins
    anyway.** Seen on the floor 2026-10-26: pairing the controller with the
    wall switch off spun the lidar up (it is USB powered from the Pi, so the
    switch never cuts it) and the dashboard showed rail ON / gamepad connected,
    WAITING FOR ROBOCLAW, motor UNKNOWN STALE, encoder READ FAIL, loop STALE.
    Battery reports the rail on from MOSFET state (`robot_battery.py:243-260`);
    motion sits "waiting for RoboClaw" (`robot_motion.py:338-366`); intents
    fail after 8 s (`:724-730`); nav goals go to Nav2 and fail for lack of
    progress; the lidar follows the MOSFET flag
    (`src/ros_nodes/lidar_status_node.py:47-52`).
    Fix: the lidar and the rail display follow "motor board answering" (robot-
    motion already knows), not the MOSFET flag; battery publishes reason
    `roboclaw_silent` after a few seconds of rail on with no board.

19. **Fresh battery, rail still says low-voltage cutoff.** `_rail_on` refuses
    on a remembered low voltage (`robot_battery.py:248-250`), against
    `docs/phases/body-phase-2.md`; the 3 s recovery probe can't read a voltage
    because robot-motion only opens the board with a drive command
    (`robot_motion.py:349-351`). Rail flickers 3 s every 30 s.

20. **No voltage check while the rail is on but idle**; motor loop exits on
    idle (`robot_motion.py:428-433`) and the dashboard shows the cached
    rail-off reason flagged stale (`src/robot_telemetry.py:346-348`).

21. **Several services publish at exactly the 1.0 s stale limit** and flicker:
    battery (`robot_battery.py:31`; dashboard rail row flashes STALE),
    sensors disabled/error (`robot_sensors.py:27-28`), pi-battery
    (`robot_pi_battery.py:26`), motion waiting loop (`robot_motion.py:348-351`),
    vision (`robot_vision.py:32`); hub rule `robot_telemetry.py:298-303`. The
    gamepad path has no hold (`robot_battery.py:201-209`), so one slow hub tick
    toggles the rail.
    Fix hint: publish at ≤0.4 s; give the gamepad path the 5 s hold.

22. **If the hub dies mid-drive, robot-motion keeps the last readings as live
    forever** (`robot_motion.py:275-292`).
    Fix hint: age readings locally.

23. **The robot spins on its own after boot or a nav restart.** AMCL-active
    edge → no remembered pose → relocalize with two full turns
    (`nav_node.py:219-223,366-373`). nav-pose.json is on tmpfs so every boot
    does this; `restart_robot_nav` may fire the edge twice (`:560-565`).
    Fix hint: relocalize only when a trip asks.

24. **Long silent waits on a goal**, up to ~75 s: 20 s for scans, two spins,
    then 30 s for Nav2 (`nav_node.py:97,437-443,734-751`), dashboard just says
    "navigating". Bridge replies "accepted" instantly; the real outcome only
    shows in later status. Resume needs a pose (`:680-683`) that may not exist
    after a nav restart → "nav2_unavailable".
    Fix hint: publish the wait reason in the goal state.

25. **Any voice motion during a trip pauses Nav2 and cancels the trip** via the
    wheels lock (item 13); `navigate_to` is refused "wheels_busy" for 2 s after
    any intent (`nav_node.py:715`); the motion bridge has one pending slot so a
    relocalize spin and a voice turn answer "busy" to each other; relocalize
    holds busy through 40 s intent waits and 10 s service calls
    (`nav_node.py:470-481`).

26. **Dashboard lidar override is confusing.** Edge-based on rail changes
    (`lidar_status_node.py:105-146`): "Turn off" silently reverts at the next
    controller reconnect or trip; "Turn on" with the rail off brings Nav2 up
    (`nav_node.py:680-683`) with nothing to turn it off; a refused transition
    is never retried.

27. **Hygiene:** lidar-status forks `systemctl is-active` four times a second
    (`lidar_status_node.py:153-172`); redeploy stops robot-lidar for
    telemetry/lib changes so the motor free-runs with no driver
    (`redeploy-robot.sh:34-35,95-99`); the hub never prunes dead sources
    (`robot_telemetry.py:186`); lidar gate is absent for the first 2-4 s of a
    drive (`safety_gate.py:18,102`) and the lidar spins whenever a controller is
    paired.

## Architecture: what these collapse into

Most of the list is four root causes, not thirty-eight bugs.

### A. The conversation owns the body (items 1-12, 17 partly, 24, 25)

A voice turn is one straight line: model text → run tools in order → second
model call → reply. While a tool runs, the turn is "busy", the robot counts as
"speaking", the text-to-speech socket is held open, the 120 s clock runs, and
nothing can arbitrate. Motion and navigation are long-running physical things
that got wedged into a request/response slot built for web search.

Core change: **body actions become events the conversation reacts to, like
speech.** `move`, `turn`, `navigate_to`, `scan`, `express` return at once with
"started" (or a refusal). robot-motion and the nav bridge already publish their
state over telemetry; robot-voice subscribes and feeds "motion finished",
"arrived", "trip failed: blocked" into the session as a new input, the way a
user utterance is. Consequences:

- Tools finish in milliseconds, so the turn ends and the robot can speak its
  acknowledgement first (1), talk and listen while driving (2, 3), close the
  TTS socket normally (4), never hit the turn timeout on a tool (5).
- "Stop" becomes a direct body command, not a model decision (6, 7, 10).
- Progress narration is just another event turn (9); scan is a chain of events
  (11); the post-move photo becomes something the model asks for (8).
- `check_navigation` and the blocking poll go away; the goal runner reacts to
  the arrival event (24).

This was already decided in `2026-06-13 - robot-state-architecture.decisions.md`
(an event path from telemetry into the brain) and never built. It does not
need a new service: one subscriber loop in robot-voice that turns telemetry
transitions into session inputs is enough.

### B. "Someone has the wheels" means three different things (13, 25, 30, 31)

The wheels lock is raised by every motion intent, including the relocalize spin
that a trip itself requested, and the nav node reads any lock as "the user took
over, cancel the trip". Teleop takeover, a voice wiggle, and a spin the trip
asked for are the same signal.

Core change: **one explicit body activity, published once**: idle / teleop /
intent / localizing / trip. robot-motion already arbitrates the wheels; it
should publish *why* it holds them. The nav node cancels only on teleop,
pauses on a voice intent, and ignores its own relocalize. The dashboard and
voice read the same word to decide which buttons and tools make sense. This
merges with A: the activity transitions are the events the conversation reacts
to.

### C. Fresh is not the same as healthy (14-22, 27)

Telemetry liveness is "published within 1 s". Every source encodes health
differently: sensors send an empty list, battery reports the MOSFET not the
board, gamepad reports connected with a dead reader, publishers run at exactly
the stale limit. Consumers that gate safety or power read freshness and assume
health.

Core change: **every source publishes an explicit `ok` plus reason, and
anything that gates safety or power requires fresh AND ok.** Publish at half
the stale window as a convention. Smaller follow-on: the rail is turned on by
inferring intent from "controller connected"; making it an explicit power
request from whoever wants the wheels (teleop, voice intent, trip) would make
the wall-switch-off case reportable and stop idle controllers and tests from
driving it. That is a bigger change than the `ok` field and can wait.

### D. The dashboard has no shared picture of the robot (28-38)

Each panel reads raw snapshot fields, each button is enabled regardless of what
the robot is doing, and every error goes to a log line that may be paused.

Core change: **one derived view built from the snapshot** (per-source
fresh+ok from C, body activity from B, nav goal state) that every panel
renders from and every button's enabled state comes from, with action errors
shown beside the button that caused them. Rendering wrapped once so one
panel's exception does not freeze the rest.

### Order

B first (small, fixes the trip-cancels-itself bug and gives the activity word
A needs), then C's `ok` field (safety), then A (the big one, mostly deletion of
waiting code), then D on top of B and C.
