# TUI Dashboard Decisions

## Context

The robot is currently systemd-first with framework-agnostic Python drivers and a future ROS2 migration path. `gamepad-teleop.service` is the active robot-control service, using an Xbox 360 controller, `ControllerDriver`, `GamepadTeleopPolicy`, `DifferentialDriveMixer`, and `MotorDriver` over RoboClaw closed-loop speed commands.

Telemetry already available in code:

- RoboClaw main battery voltage via `MotorDriver.get_battery_voltage()`.
- RoboClaw motor currents via `MotorDriver.get_currents()`.
- Encoder wheel speeds via `MotorDriver.read_wheel_speeds()`.
- Controller connectivity and full normalized controller state via `ControllerDriver`.
- Service logs through journald.

Telemetry not clearly available yet:

- Pi power-bank charge percentage or voltage. The current docs describe a USB-C PD power bank on a separate rail, but no readable fuel-gauge/UPS HAT/I2C sensor is listed.

## Decisions

### 1. Telemetry Ownership

Decision: the dashboard should be observe-only for normal operation.

Robot services should own hardware access and publish or expose telemetry for the TUI to read. The dashboard should not independently open the RoboClaw serial port or controller input device while `gamepad-teleop.service` is running.

Reasoning:

- Matches the current architecture: drivers stay framework-agnostic, services own process lifecycle and hardware wiring.
- Avoids serial/input ownership conflicts with `gamepad-teleop.service`.
- Maps cleanly to the future ROS2 version, where the TUI can subscribe to topics instead of touching hardware.
- Leaves room for an explicit foreground debug mode later, where services are stopped and a diagnostic process owns hardware directly.

### 2. Pre-ROS2 Telemetry Transport

Decision: use a Unix domain socket for live local telemetry.

The normal dashboard path should avoid repeatedly writing state snapshots to disk. Robot services should expose live telemetry over a local Unix socket, and the TUI should connect as a read-only client.

Reasoning:

- Avoids unnecessary SD/NVMe writes during robot operation.
- Keeps telemetry local to the Pi and avoids network exposure by default.
- Is a closer match to the future ROS2 subscription model than direct hardware reads.
- Keeps the implementation lighter than introducing ROS2 or HTTP just for a terminal dashboard.

### 3. Telemetry Topology

Decision: add a separate `robot-telemetry.service` hub.

Robot services should publish state to a telemetry hub, and the TUI should subscribe to that hub instead of talking directly to each hardware-owning service.

Reasoning:

- Keeps `gamepad-teleop.service` focused on safe robot control rather than dashboard backend duties.
- Gives future sensor, audio, perception, and autonomy services a single place to publish telemetry.
- Gives the TUI one stable stream to consume.
- Maps naturally to the future ROS2 model, where the hub can be replaced by topic subscriptions.

### 4. Pi Power-Bank Telemetry

Decision: first implementation should show Pi power health, not a fake power-bank percentage.

The dashboard should show reliable Pi-side health signals such as undervoltage/throttling status, uptime, load, memory, disk, and SoC temperature. It should mark power-bank charge percentage as unavailable until the robot has readable power hardware.

Reasoning:

- The documented Pi battery is a plain USB-C PD power bank with no known readable fuel gauge.
- Estimated charge percentage would look authoritative while being weakly grounded.
- Kernel/firmware health signals are still operationally useful, especially for catching undervoltage or thermal throttling.

### 5. Motor Battery Display

Decision: show RoboClaw/motor battery as pack voltage, estimated per-cell voltage, and status bands. Do not show a percentage.

The dashboard should display the 3S LiPo pack voltage from RoboClaw, derive estimated per-cell voltage by dividing by 3, and show clear OK/low/critical status bands.

Reasoning:

- RoboClaw gives a real pack-voltage reading.
- LiPo percentage inferred from voltage is approximate and can be misleading under motor load.
- Per-cell voltage is directly meaningful for the documented safety thresholds.
- The configured motor rail cutoff is 10.5V pack, with warning at 10.8V.

### 6. TUI Stack

Decision: use Textual/Rich for the dashboard UI.

Reasoning:

- Supports a polished multi-pane terminal dashboard without hand-building a curses framework.
- Fits live status widgets, color-coded alerts, semi-graphical controller state, wheel metrics, and log panes.
- Adds dependencies, but they are appropriate for an operator-facing TUI rather than hardware-driver code.

### 7. Dashboard Launch Model

Decision: the TUI should be a foreground SSH tool.

The dashboard should be launched manually, for example as `robot-dashboard`, when operating or debugging the robot. It should connect to the always-running telemetry hub and exit cleanly without affecting robot services.

Reasoning:

- An interactive Textual app is most natural as a foreground terminal process.
- Operators can connect and disconnect without changing robot behavior.
- Keeps systemd focused on robot services and telemetry, not terminal session management.

### 8. Log Integration

Decision: the dashboard should tail journald for selected robot services.

The first implementation should include a log pane backed by `journalctl`, covering at least `robot-telemetry`, `gamepad-teleop`, and `robot-brain`.

Reasoning:

- Matches the repo's current logging model.
- Avoids duplicating log/event infrastructure before the telemetry hub has proven its shape.
- Keeps raw operational logs available while the structured telemetry stream handles current robot state.

### 9. Dashboard Actions

Decision: the first dashboard should be strictly read-only.

The TUI should show status, metrics, controller state, and logs, but it should not send robot commands or manage services in the first implementation.

Reasoning:

- Keeps the operator dashboard safe and low-risk while the robot is moving.
- Avoids designing a command/authorization/safety protocol before there is a clear need.
- The telemetry protocol can stay extensible so future write operations can be added deliberately.

### 10. Telemetry Update Rate

Decision: target 5 Hz for the first live telemetry stream.

Reasoning:

- Keeps terminal redraws calm over SSH.
- Is enough for operator awareness of controller state, wheel metrics, battery status, and service health.
- Avoids coupling dashboard updates to every 50ms teleop control-loop tick.

### 11. V1 Telemetry Scope

Decision: include gamepad teleop state plus system health in the first structured telemetry stream.

The first implementation should cover controller state, wheel targets and actual wheel speeds, RoboClaw voltage/current, service heartbeats, and Pi health.

Reasoning:

- Focuses on telemetry the current robot can produce.
- Keeps the dashboard useful during manual operation.
- Avoids placeholder-heavy UI for future sensors, audio, or autonomy services that do not exist yet.

### 12. Controller Visualization

Decision: use a compact meters/table view for Xbox 360 controller state in v1.

The dashboard should show connectivity, button states, D-pad state, triggers, and stick axes with readable labels, bars, and/or numeric values rather than a controller-shaped ASCII diagram.

Reasoning:

- Prioritizes clarity while driving/debugging over novelty.
- Makes analog values easier to inspect.
- Leaves room to add a richer controller diagram later once the telemetry and layout are stable.

### 13. Wheel Metrics

Decision: show all currently available wheel metrics in a compact table.

The dashboard should show normalized left/right command, target QPPS, actual encoder QPPS, target-vs-actual error, motor current per side, and stale/read-failure status.

Reasoning:

- Helps distinguish bad input/mixing, motor controller command issues, encoder feedback issues, and electrical load problems.
- Raw QPPS is useful during robot bring-up and PID tuning.
- Staleness/read-failure status prevents old telemetry from looking current.

### 14. Unix Socket Wire Format

Decision: use newline-delimited JSON snapshots/events over the Unix socket.

Reasoning:

- Human-inspectable with simple tools.
- Easy to test with standard Python.
- Avoids Python-specific or opaque boundary formats.
- Keeps the data model close to structured messages that can later map to ROS2 topics.

### 15. Missing or Stale Telemetry

Decision: keep last known values visible, but mark stale or disconnected state prominently.

Reasoning:

- Preserves useful context when a service disconnects or restarts.
- Avoids old values silently looking live.
- Makes service and publisher failures obvious without causing the whole dashboard to become blank.

### 16. Drive Loop Priority

Decision: telemetry must never delay the motor command heartbeat.

The teleop service should keep `set_wheel_speeds()` as the priority operation. Optional telemetry reads such as wheel speed feedback, motor currents, and battery voltage should run only on the slower telemetry tick, and they can be skipped, marked failed, or sampled less often if they risk delaying the next speed command.

Reasoning:

- The current `gamepad-teleop.service` is the active robot-control path.
- Dashboard usefulness should not come at the cost of motor safety or command freshness.
- RoboClaw readbacks are useful diagnostics, but they are not required to keep driving safely.

### 17. Hub Simplicity

Decision: the v1 telemetry hub should be concrete, not framework-like.

The first hub should accept `gamepad_teleop` updates, sample Pi health, keep latest values in memory, and broadcast one merged snapshot. It should not introduce a generic telemetry framework, plugin model, schema registry, or event bus.

Reasoning:

- The repo's current architecture favors small service wrappers around framework-agnostic drivers.
- V1 has one external publisher plus local Pi health, so a generic abstraction would add more surface area than value.
- A concrete hub is easier to replace with ROS2 topics later.

### 18. Publisher Failure Semantics

Decision: telemetry publishing is best-effort.

If the telemetry hub is unavailable, slow, or restarting, robot services should drop the current telemetry update and continue their primary behavior.

Reasoning:

- Keeps the dashboard observe-only in practice, not just in UI.
- Prevents telemetry infrastructure from becoming part of the safety-critical drive path.
- Matches the future ROS2 expectation that transient subscriber or transport issues should not stop the motor control node.
